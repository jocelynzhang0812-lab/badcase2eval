# x35 工具使用规范

> 本文档记录 x35 模型各种 tool 的预期效果和使用规范

---

## Data source tool

### 该调用的时候才调用

- 能正确调用 `get_data_source_desc` 和 `get_data_source` 两个 tool
- 能根据 tool description 选择正确的 data source API
  - **个股金融**：调用 ifind、Yahoo finance、binance
  - **宏观经济**：调用 world bank
  - **学术搜索**：调用 Google scholar、arxiv
  - 部分信息网搜如果能搜到，也不算错
- 有多个对象/多个数据需要查询，一次调用不能满足的，需要多次调用
- 一次调用就能满足用户需求的，不要多次调用

### 调用时不要吐错参数

- 参数需要严格根据用户 query 请求吐（时间、查询对象、查询内容需要一致）
- 参数格式需要严格遵循每个 data source API 的 description 以及示例：
  - ifind 的 A 股股票代码格式为 `XXXXXX.SH/SZ` 等，Yahoo finance 的为 `XXXXXX`
  - worldbank 的国家代码为 iso 三字母格式
  - required 参数必须要吐
- 如果用户要求多个不连续、时间间隔很大的数据，要分开调用，不要请求时间跨度很长的区间数据
  - 例如：用户要求 1961、1992、2015 三年的数据，不要请求 1961-2015

### 调用后的读取处理

- **只在必要时**（file preview 不完整，且用户需要额外的分析和计算），才使用 python 进行读取和分析；否则直接回答用户的问题
  - 目前很多 badcase 是只要拿到了数据就开始调用 Python
- **文本类信息**（Google scholar、arxiv）尽量不要使用 python 进行处理和分析，而是直接根据 context 回答用户的问题
- python 分析数据时，只做必要指标和统计指标等分析计算
  - 目前的 badcase：通过 Python print 来输出文本、动不动就 Python 画图

## Image search tool

### 文搜图

- **能分辨搜图和生图需求**：在用户要求 AI 生成类图片时，要用生图工具，而不是搜图工具
- **能给出合适的搜图关键词**：
  - 关键词应与上下文高度相关
  - 关键词要具有明确指向性和细节，避免过于宽泛，尽量使用**实体词+限定词**的组合
    - 例如："黄忠"过于宽泛，"三国 黄忠"是合适的关键词
  - 多轮对话，需结合上下文来编写关键词
  - 关键词应该保证能在搜索引擎准确找到合适图片

### 图搜图

- **能分辨 "图搜图" tool 和 search tool**：用户问题中带图，如果只是需要了解图中提到的某个文本信息，就用 search tool 去搜索网页；如果是需要"找类似图片/找图片所在的 URL"等，才用"图搜图"tool

### 回答中插图

- 能 follow system prompt 里关于插图的要求，要求插图的时候插图，要求不插图的时候不插图
- **能在合适的场景下插图**：
  - **不适合插图**：代码、表格、政治、引人不适、抽象概念等
  - **适合插图**：旅游、美食、动植物、购物、公众人物、艺术设计、运动姿势、家居装修等
- **能在合适的位置插图**：
  - 在相关段落的**后面**插图，且图片和上面的段落是明显相关的；不要把所有图片都插在回答的最后
  - 如果有必要，每个段落后可以插多张相关图片
  - 图片和文字不要有多余的空行、奇怪的标志符，要保持全程统一

### 结合 Python 使用

- 在适当的时候，使用 Python 去放大/缩小/剪裁图片，以得到更好的搜索结果

## Search tool

### 线上现状

- 用户关闭了联网开关，一定不搜
- k2(含turbo)：
  - n2s 在 history 中改造成了 search tool 格式
  - n2s 后面都带 search tool
  - 文件 / url 场景，无 n2s，带 search tool，之后的轮次也带
  - 带图场景，无 n2s，无 search tool（K2 目前无 vision 能力）
- k2 thinking：在上述基础上增加一条：n2s = false 即判断不搜时，不带 search tool

### 搜不搜

- 能 follow system prompt 里关于搜不搜的限制
- 能 follow system prompt 里关于多搜/适当搜/少搜的限制
- **该搜的时候搜，不该搜的时候不搜**：
  - **不带附件场景**：遵循 N2S 搜不搜价值观
  - **带文件/url 场景**：如果可以靠自身知识回答，就直接答；如果需要搜索，就搜索
  - **带图场景**：如果可以靠自身知识回答，就直接答；如果需要搜索，就搜索
    - **拍照解题**：尽可能别搜，大概率用自己的知识解题效果更好
    - **拍照识物**："这是啥""这是谁"
    - **以图搜图**："找类似图片""这是电视剧里的哪一集"

### 怎么搜

- **能输出合理、高效的搜索词**（详见 N2S 搜索词价值观）
- 能用对搜索语言
- 能正确使用 site、filetype、时间筛选等限定词来使用高级搜索
- **该多步搜的时候，去多步搜**：
  - 尽可能在保证准确性的前提下，用更少的步数完成对用户的回答
  - 当用户的问题需要非常多轮的搜索时（例如，大于 20 轮），在合适的时候停下，询问用户是否需要继续搜索
- 当提供多个垂类搜索工具时，能正确使用合适的那一个（医疗搜索、学术搜索、财经搜索、公众号搜索、播客搜索、PDF 搜索等）

### 怎么答

#### 不要编造

- 尽可能的帮助用户查到准确的信息，当极尽可能仍然查找不到准确信息时，客观承认自己没有找到相关信息，绝不能胡编乱造
- 回答要遵循原文，对于冲突的信息，优先引用权威信源内容，如果不能判断权威性，可以适当向用户展示信源间的冲突（A 信源说xxx，B 信源说 xxx）

#### 引用

- 能 follow system prompt 里关于引用的要求
- **能给出正确的引用**：不会给出不相关的标号，也不会引用了但不给标号；连续的多句话引用同一个网站时，只给一个引用标号
- **能灵活调整引用的格式**：例如 `[^1^][^2^]` 或 `[source name](URL)` 或 `[turn2search1]` 或 `<citation index="0,5">content</citation>`
- **能灵活调整引用序号的密度和位置**：
  - 只放在段尾、只放在句尾、放在句子任何位置
  - 禁止放在句子开头
  - 高密度引用（每句话都引用）、中密度引用（关键陈述才引用）、低密度引用（重要关键陈述才引用）
- **能在回答中输出引用原文**：如果在 system prompt 中规定了"回答如果参考了网页内容，必须要原封不动输出原文，不能改写"，要能 follow 这一指令

#### 时效性、权威性、相关性

- **对于有时效性要求的问题，优先引用新内容进行回答**
- 优先引用权威性高的内容进行回答
- 只引用相关的内容进行回答

**️ 时效性检查要点（非常重要！）：**

分析时必须检查以下三个时间点：

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│   当前时间      │────→│   搜索关键词    │────→│   搜索结果      │
│  (今天几号？)   │     │  (年份正确？)   │     │  (日期合理？)   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

**检查清单：**

| 检查项 | 说明 | 示例问题 |
|--------|------|----------|
| **当前时间** | 确认分析时的实际日期 | 今年是2026年不是2025年 |
| **搜索词时间** | 检查搜索关键词中的年份/时间 | `"2025年新闻"` 在2026年就是错误的 |
| **结果时间** | 验证搜索结果日期是否合理 | 结果中出现未来日期，或过于陈旧的日期 |

**常见错误案例：**

```
 错误案例：
   当前时间：2026年2月9日
   搜索词："2025年2月最新新闻"  
   结果：返回2025年2月的新闻（已过时1年）
   问题：搜索词年份错误，导致结果不满足"最近"需求

 正确做法：
   当前时间：2026年2月9日
   搜索词："2026年2月最新新闻" 或 "最近一周热点"
   结果：返回2026年的新闻
```

**时间错误归类：**
- 搜索词年份错误 → `intent_misunderstanding` 或 `execution_logic_error`
- 搜索结果时间不合理 → `factual_error` 或 `outdated_info`
- Agent 未校验时间 → `execution_logic_error`

## Fetch URL tool

### 线上现状

- 只有开了【联网搜索】开关，才会带 fetch URL tool
- 用户传图/URL/文件时，会自动关闭【联网搜索】开关，也就没有 fetch URL tool

### 该调用时调用

- 需要基于 URL 内容去回答时，调用 fetch tool
- 否则，不调用 fetch tool

### 学会和 search tool 同时调用

- 目前线上模型用了 search 就不会用 fetch tool 了，希望 x35 能学会在一个 segment 同时用 search 和 fetch，灵活调用和切换

### 能 fetch 回多模态的完整内容

- fetch URL 无论是网页、文件、图片，都能以图文混排形式 fetch 回来

## Ipython

### 使用场景

| 场景 | 输入 | 输出 | Query 描述 |
|------|------|------|------------|
| 学生作业 | Excel | Excel | 【数学计算】 |
| 文件整理 | Excel | Excel | 【多文件】舞蹈培训班老师整理资料 |
| 数据处理 | Excel | Excel | 【复杂文件结构】对 Excel 数据二次加工 |
| 财务分析 | pdf | text | 【长文件+数学计算】财务报告分析 |

### 读写文件类

- 用于读取、处理、生成各类文件
- Excel 操作常用 pandas/openpyxl
- 文档处理支持多种格式

### 数学运算类

- 复杂数学计算
- 数据统计分析
- 财务计算等

|-------------|----------------|

| **搜索词年份错误** | `execution_logic_error` |

| 引用格式错误 | `format_mismatch` |
| 编造搜索结果 | `hallucination` |
| 时效性错误 | `outdated_info` / `factual_error` |
| Fetch URL 时机错误 | `wrong_tool_selection` |
| 工具调用顺序错误 | `execution_logic_error` |
